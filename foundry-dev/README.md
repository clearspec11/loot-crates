# Checking against a real Foundry world

The live checks run the branch's code in a real dev world, the way a player and a GM would: they click the real buttons, then report what happened as JSON. Use them for anything that touches the purchase path, refunds, the data model, sheets, sound, the manager or the shop.

## Running a check

One-time setup:

```
cp .env.example .env        # then fill in FOUNDRY_URL and MODULE_BASE
npm run foundry:serve &     # serves this checkout's module/ on port 8766, with CORS
```

Then, with nobody logged in to the dev world:

```
npm run live -- --list               # every check, with what it covers
npm run live -- live-dice            # run one
SEAL=1 npm run live -- player-pull   # env for one run goes before npm
npm run live -- live-reveal --shot out.png
```

The world needs a Gamemaster with no password and a player (default Player2, or `PLAYER` in `.env`) who owns a test character in the Actor folder "Loot Crates Test". Checks restore what they change in a `finally`, and make at most one purchase per run.

## The checks

## Windows that close by themselves

A finished reveal or table window closes after each client's **Close finished game windows** delay (the `closeFinished` client setting, 30 s by default). A check that reads a reveal or table window after it lands must not depend on that: it turns closing off for the run on every page it drives with `checks/lib/linger.cjs` (`keepWindowsOpen()`, then `hold(page, label)` after each join and `restore()` in its `finally`), and reports `closeFinished` per page with `restored: true`. live-auction, live-deck, live-dice, live-roulette and player-pull do. A check that reads its window only at the landing or a few seconds after it (live-box-price, live-copy, live-delete-round, live-limits, live-price, live-sound, live-starter, live-table-crate, live-well, live-well-day) doesn't need it yet, and takes it up once it reads later; live-linger, which checks the closing itself, must not use it.

## How they work

`run.cjs` joins a world as its Gamemaster in headless Chromium and runs a script as an async function body in the page, printing its return value as JSON. `serve-module.py` serves this checkout's `module/` folder with CORS so the script can `import(MODULE_BASE + "scripts/core/odds.js")` and test the working copy without installing anything on the Foundry host. Without `npm run live`, the same run by hand is:

```
python3 foundry-dev/serve-module.py module 8766 &
FOUNDRY_URL=http://<foundry>:30000 MODULE_BASE=http://<this machine>:8766/ \
  NODE_PATH=$(npm root -g) node foundry-dev/run.cjs foundry-dev/checks/live-pull.js
```

`run.cjs` takes a file path or a check's bare name in `foundry-dev/checks/`: `run.cjs live-tabs` (or `live-tabs.js`) runs `foundry-dev/checks/live-tabs.js`. A name that is neither a file nor a check there stops with an error naming the checks folder.

Needs Playwright with Chromium 146 or newer (Foundry v14 refuses older) and a Gamemaster with no password: a dev world only. `checks/live-pull.js` does one real purchase on a test actor in the "Loot Crates Test" folder and reports the purse and the granted item. `checks/live-refund.js` does one pull at a fractional price, writes the log row, refunds it with `refundPull`, and reports that the purse is back to the same copper in whole, consolidated coins, the granted item is gone, the box's stock is restored, and a second refund changes nothing. `checks/live-refund-focus.js` does one pull, then refunds it from the manager's Pull log as a GM would (Refund, then Yes) and reports the purse and where keyboard focus lands (the row's "refunded <date>" status inside the log table). `checks/live-reveal.js` plays the reveal window with a strip built from the items compendium, writes nothing, and reports how far the landed card sits from the marker (`--shot` for a screenshot). `checks/live-missing.js` saves a test pool with one legendary entry pointing at a dead UUID, buys one crate through the GM's socket path, and reports the odds before and after (legendary gone), that the purse was charged once, and that the pool setting now flags the dead entry `missing: true`. It then opens the manager and reports the pool editor's rows: dead entries show "Source missing" (one the last sweep hadn't seen is flagged by the render), stale names show "was <old name>" with Update, the Boxes tab's odds leave the dead entries out, Update copies the source's name, and an item dropped on a missing row relinks it with its weight kept (`--shot` shows the pool). `checks/live-drop.js` makes sure an Item folder "Loot Crates Test" holds two test items, runs `entriesFromDrop` on the dnd5e.items compendium, that folder and a dnd5e.tables roll table, adds the first two to a test pool and reports the entries added; it then drops the folder on a second pool in the manager and clicks Add in the preview, drops the compendium and leaves its preview open (`--shot` shows it), and lists the packs the compendium picker offers. `checks/live-edits.js` makes no purchase: it opens the box editor, takes one from stock through the write queue while the dialog is open and saves a new price (stock stays lowered), opens a pool's rename dialog while a sweep flags its dead entry (the flag survives the rename), and relinks that entry with its Relink button and a typed UUID (weight kept). `checks/live-pool-users.js` makes no purchase: it saves a test pool with one item and a test box that draws only from it, reads the pool's header line ("In Live users check crate"), clicks the pool's Delete and then its item's Remove, reads each DialogV2 confirm for the box's name and "will have nothing inside", and clicks No both times (the pool and item must still be there).

`checks/live-edit-entry.js` makes no purchase: it saves a test pool (two uncommon dnd5e items, four weapons whose source has no rarity) and a box, and in the pool editor sets one entry to Legendary at weight 3 and another to weight 0 through the rows' own controls. It reports the stored entries, the row and header text ("Never drops", "No rarity set", "Set rarity for 4 unset"), the box odds before and after (Legendary in), 400 seeded draws (the weight-0 entry never drawn), and that a source sweep leaves the overridden entry ok, not renamed (`--shot` shows the pool).

`checks/live-sweep.js` makes no purchase: it registers the module's index fields as init does, warms dnd5e.items' index once, makes the call dnd5e's compendium browser makes (its own field list), then builds or reuses a pool of every dnd5e.items entry and times `checkSources` and `refreshMissing` twice each (every warm call must be under 1000 ms). It reports that the entries keep the tiers their index rows give and that the count flagged "No rarity set" matches the rows with no rarity, empties that pool again, puts a world Item with an empty `system.rarities` (created once in the Items folder "Loot Crates Test") into a small pool as an older entry and shows the editor flag it "No rarity set" after a sweep, and reports the "Live UI pool" entries learning their `sourceRarity` (`--shot` shows the editor).

`checks/live-big-pool.js` makes no purchase: it saves a pool of every dnd5e.items entry (872), opens the manager and times `render({force:true})` as render plus forced layout and as two animation frames less an idle two-frame baseline (both under 300 ms; the headless runner's software canvas makes two idle frames take ~500 ms). It reports that the big pool starts collapsed with its census in the summary and no rows, draws 50 rows when opened, that the "No rarity set" chip shows only unset rows, that a "wand" search plus one row set to Rare is stored by updatePool with focus kept, that the search and the Rare chip survive a full re-render, and that Show more draws rows 51-100 with focus on row 51. It empties the pool again at the end (`--shot` shows the open pool).

`checks/live-box-odds.js` writes nothing: it opens the box editor for the first box with a live pool, reads the preview pills, types a new weight with input events, unticks every pool (the "can drop nothing" line) and ticks them back, and reports the pills each time and that the stored box is unchanged; the dialog is left open in `THEME` (edit it to "light") for `--shot`.

`checks/live-focus.js` makes no purchase: it saves a pool of every dnd5e.items entry, types in its search and re-renders the manager before the search debounce runs (as a late source check does), then re-renders with focus on a row's rarity select. The typed text must survive with focus still in the search, and focus must come back to the same row's select. It empties its pool at the end.

`checks/live-shop-pity.js` saves a test pool and a 1 gp box "Live pity crate" (pity after 2, no duplicates), sets Crate Tester's pity state for it three ways and reads the shop card each time (both rarities with "within 2 pulls"; owns everything: "Nothing new for Crate Tester" on an aria-disabled Buy; due: only the guaranteed rarity, "guaranteed this pull"), checking the pills against `shopOdds` with that state. It picks Crate Tester in the shop's character select, then presses Buy once and watches every frame to the landing: the card's pity line and pills must stay as they were before the click from the GM's state write (~0.3 s into the spin) until this pull's card lands under the marker (`.lc-card--landed`), since the shop holds the result for the spin (0.7.0), and must then change to the new state within 1 s of the landing. It reports `heldAfterWriteMs`, `heldFrames` and `changedAfterLandingMs`, and that the reveal's ribbon was the odds the shop showed.

`checks/live-refund-pity.js` sets no state: it presses Buy once on "Live pity crate" in Crate Tester's shop (after live-shop-pity.js the pity is due, so the pull is the guaranteed rarity and resets the count), closes the reveal when it lands, opens the Pull log by clicking its tab, presses the new row's Refund and Yes, and reports Crate Tester's state for the box (must equal the state before the pull), the open shop card's pills and pity line (must equal the card before the pull, within 1 s of the state write), the dialog's pity and "can drop again" sentence, the purse and that the granted item is gone.

`checks/live-shop.js` makes no purchase and writes nothing: it opens the Crate Shop for Crate Tester and reports each box's pills, colour and Buy state, failing on any pill that reads 0% or has no rarity name, a box coloured above the best rarity it can drop, or an unbuyable (aria-disabled) Buy without an aria-describedby reason shown as visible text, or any Buy with a real `disabled` (it couldn't keep focus) (`--shot` shows the shop).

`checks/live-payoff.js` buys one crate as the GM through `requestPull` and reports, from the real reveal: the button reads Skip and is enabled mid-spin, the strip is aria-hidden, the result says "Added to <actor>'s inventory" and "<n> gp left", focus is on Close after landing, Open item renders the granted item's sheet, and the newest chat card's content link resolves via `fromUuid` to the granted item. It then opens two reveals with distinct requestIds (no purchase), reports their origins (cascaded, not stacked), closes the first mid-spin and confirms its chat card still posts.

Every check loads the branch's words first, as main.js does: once the world is ready, `run.cjs` and each headless script import the branch's `scripts/core/i18n.js` and call `loadStrings()`, which fetches the branch's own `lang/en.json` from `MODULE_BASE`. The installed release may have no language file (1.0.1 has none) or older words, and the branch's scripts read every sentence by key (`i18n.js`), so without it a check would see keys like `LOOTCRATES.Shop.Title` where the text should be.

Rules for the dev world: test actors only in that folder, never delete anything, never touch other folders' actors.

`checks/player-pull.cjs` times a real player purchase: a headless Gamemaster and Player2 both run the branch's socket code, and Player2 buys through the shop (`COUNT=3` buys three in a row; the first follows a fresh GM page load and its load-time sweep). It reports, per purchase, the click-to-reveal and click-to-landed times, the Buy button's labels over time, where keyboard focus is (`focus`: the Buy is focused before the click; after the GM's charge it must still be that same Buy node or the reveal's Close, Close on landing, and the Buy again once the reveal is closed; `focus.ok` sums it up), whether the shop, the reveal and the pull's chat card read in words at the landing (`words.keysShown`: any `LOOTCRATES.` key shown in their text, none for `words.ok`), and the GM's per-step timings (`loot-crates | pull … timings (ms)`, a `console.debug` line socket.js always writes). Both clients also wire the branch's redraw listener as main.js does (open windows follow the world settings). `GM_LOG=1` opens the manager's Pull log on the headless GM first and reports `gmLog.rowMs`, from the click to the new row in the GM's `.lc-table` (within 2 s). `CLOSE_SHOP=1` buys nothing: the GM clicks the manager's shop toggle while the player's shop is open, and `closeShop` reports how long the player's Buy took to turn off with the notice naming the closed shop (within 2 s), then opens the shop again the same way. `SEAL=1` (with a `BOX` that has a pity rule, such as "Live pity crate") first opens the player's character sheet from the Actors sidebar and its Inventory tab, and `seal` reports the granted item's row: never visible in any animation frame before the landing (`leakFrames` 0), hidden at reveal +1 s with the shop card's pity text and odds as they were before the click, and visible at landed +0.5 s with the card showing the new state. With that sheet open the reveal reaches the player in ~2.4 s instead of ~0.5 s on this VM: dnd5e re-renders the sheet for the charge and again for the item, ~0.9 s each in software (`longTasks`, `sheetRenders`). Both clients' canvas ticker is paused unless `CANVAS=on`: headless Chromium draws the canvas in software, which on this VM makes every await on either page wait 0.5-1.4 s.

`checks/live-price.cjs` checks that a player is charged only the price on the Buy they pressed. Two headless clients run the branch's socket code (the Gamemaster seat must be free; it exits 2 when a person holds it). With Player2's shop open, the Gamemaster raises "Live UI crate"'s price in the manager as a person does (the Boxes tab, Edit, the price field, Save). Meanwhile the world's broadcast of that setting is held back on the player's WebSocket (Playwright `routeWebSocket`), so the shop still shows the old price. This is what happens to a pull already in flight when the GM saves. The player clicks that stale Buy. The check expects the shop's notice line to say "… now costs N gp (you pressed M gp). Nothing was charged." (the sentence the shop gives a stale price it catches itself), no toast, and the purse, items and Pull log unchanged. It then lets the broadcast through, waits for the Buy to redraw to the new price with the line still up, and clicks again: the line goes, and the check expects exactly the new price to be charged, with a log row at that price. Finally the GM puts the old price back the same way. One real purchase per run.

`checks/live-well.cjs` checks the Wishing Well (well.js) at a real table, with the branch's code on both headless clients (the Gamemaster seat must be free). The GM seeds "Live well" (1 sp a throw from "Live UI pool", odds nothing 100, a cap of five throws more than Crate Tester has already thrown today, since the cap is per in-game day and the day doesn't turn between runs) and notes the world time, purse and log. Player2 presses the well's Throw five times in Crate Tester's shop, each reveal landing (`.lc-well--landed`) with "The coin sinks. Nothing." in the window's live region and no Watch again; the card counts "n of cap throws today" and after the fifth reads "The well is still until tomorrow (cap of cap today)" with its Throw off. No chat card may post; the purse must drop by exactly 50 cp and five rows carrying today's key (`day`) must be in the log. The GM then advances the world a day with dnd5e's calendar HUD (+1 day; the HUD is shown for the check if the world has it off and put back): the player's card must drop the still line within 2 s, and turning the day back brings it back. Then the GM opens the Pull log by its tab, presses Hide misses (pressed, the folded row gone) and presses it again (unpressed, back), and Refund one then Yes on the folded "5 throws, nothing" row: the purse gains 1 sp, the row reads one throw fewer and the player's card "cap-1 of cap throws today" within 2 s. The world time, the calendar settings and the well's record are restored in a `finally`. Since a day ends at a long rest with dnd5e's calendar off (clock.js), the check turns the calendar on before the first throw and puts it back after. `HIDE_GM=1` runs it with the GM's tab hidden.

`checks/live-well-day.cjs` checks that, with dnd5e's calendar off (its default), a day ends at each character's long rest. Both headless clients run the branch's socket and its `dnd5e.restCompleted` hook. The GM turns the calendar off if it is on and seeds "Live well" under a fresh id each run (its throw rows stay keyed on rest counts the `finally` puts back, so on a reused id they would count again) with a cap of one throw. Player2 presses Throw once, and the card reads "The well is still until tomorrow (n of n today)" with its Throw off. The GM long-rests Crate Tester with `actor.longRest({ dialog: false, chat: false, newDay: true })`, and the player's card must turn its Throw back on within 3 s with the world time unmoved. Then the player throws to the cap again and long-rests Crate Tester on their own client, which sends `newDay` to the GM, and the Throw comes back on again. With `CALENDAR=on` the GM turns the calendar on instead (daily recovery by the calendar), clears Crate Tester's `restedInto` entry and moves the clock to the next day's 06:00, then rests Crate Tester with `advanceTime: true` (dnd5e moves the clock eight hours, to 14:00 the same calendar day, and the Throw comes back on within 3 s). After a second throw to the cap, the player's own long rest from their client the same calendar day must leave the card shut, with the world time and the day rested into unmoved (the borrow ahead of the clock is one day at most); the GM then moves the clock over midnight into the next morning and the card must stay shut; and the player's own long rest that day, which can't move the clock, must bring the Throw back on within 3 s with the world time unmoved. Crate Tester's `days` count is never touched. The calendar setting, the world time, the well's record and Crate Tester's `days` and `restedInto` entries in the actor-state setting are restored in a `finally`. Two 1 sp throws; Crate Tester is rested twice (three times with `CALENDAR=on`).

`checks/live-importer.cjs` checks a grant Plutonium would veto (pull.js `createGrants`, kinds.js `readyToGrant`), with the branch's code on both headless clients (the Gamemaster seat must be free). The GM picks the first loot-type item in `world.imps` (`PACK=`) carrying `flags.plutonium.propDroppable` "item" (none, or no pack: the check prints `unavailable` and changes nothing) and seeds "Live importer pool" with it alone and the 1 gp "Live importer crate" drawing only from it; a watcher on the GM's page records every element added whose text is Plutonium's prompt ("Import via Plutonium?", "Yes, use the importer"). As a control, the GM first creates the item on Crate Tester the plain way: with Plutonium's prompt mode on, the prompt must appear and the creation make nothing; it is closed with its own close control and the watcher reset. Then Player2 presses the crate's Buy in Crate Tester's shop and the strip lands on the item: the watcher must have seen nothing, the purse is 1 gp lighter, the new row names the item in `itemId` and `itemIds`, and the item is on the sheet with `flags.plutonium.isStandardDragDrop` true, its other Plutonium flags kept and no second copy. The GM refunds it from the Pull log (its tab, Refund, Yes): the item is gone and the purse back. The crate is put back as it was, or taken off the shelf if the run made it, in a `finally`. One real 1 gp purchase, refunded.

`checks/live-dice.cjs` checks Dragon's Teeth (dicegame.js) at a real table, with the branch's code on every headless client (the Gamemaster seat must be free). The GM seeds "Live dice" (10 gp to roll 3d6 over the dragon's 3, so all but 1, 1, 1 win, paying 3x) and notes the purse, log and chat. Player2 presses Bet once in Crate Tester's shop; every animation frame to the landing (`.lc-dice--landed`, as the frame loop sees it) is watched for the verdict showing in the chat log (0 leaked frames) and for the pull's card showing at all (0 frames: a card posted only for a win tells by turning up, so its whole message stays hidden), and each rendering of the pull's card must be sealed and hidden until then; the reveal's faces, total and result (in a live region, "15 beats the dragon's 3 · Rolled 4, 6, 5 on 3d6 · Won 30 gp · ... in the purse") are read, and the GM's reveal, and a third seat's that joined with its tab hidden (landing at once), must show the same faces. With Dice So Nice active (it stays on for the checks: real tables use it) the stage waits blank on the 3D roll, which headless never reports, so it tells the total on the timeout and lands a frame later; a settled die's foot must keep the vault's line until the total is told and take the win's colour from then, on either path, and the run reports the path taken (`bet.path`, "3D" or "2D"). The newest chat message must carry no Roll, the purse must change by exactly payout - stake, and the log row must hold the faces and `payoutCp`. The GM then opens the Pull log by its tab, presses the row's Refund and Yes: the confirm reads "Take 20 gp back from Crate Tester?" (a win) or "Return 10 gp" (a loss), the purse returns to its start value, focus lands on the row's status and the card in chat reads refunded on the player's client. `HIDE_GM=1` runs it with the GM's tab hidden (its reveal lands at once). `MANUAL=1` sets the GM's d6 fulfillment to manual entry for the run (restored after): no manual-roll prompt may appear and the reveal must reach the player within 2.5 s. `SHORT=1` first spends the winnings (the purse set below what the refund would take back) and presses Refund: the dialog must name the shortfall ("Crate Tester has spent ... of the 30 gp won at Live dice ...
